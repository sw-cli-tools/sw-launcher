



My AI coding agents spend too much time trying to run various tools I've built that usually involve running an emulator against .s code or .bin code.  But the code to be run has varying levels: straight assembler or code compiled to assembler or assembled binary.   If the code is an interpreter written in or compiled to assembler it needs source, either loaded via UART (if small) or pre-loaded into memory.  But what if the interpreter is a p-code VM, then it needs to load binary (only pre-loaded, not via UART).  But what if the p-code app itself needs to read a large source file, e.g., basic source, when the basic interpereter is written in pascal compiled to p-code.  But what the basic program is a smalltalk interpreter?  It needs to load the smalltalk source and what if the smalltalk source acts on data that also needs to be loaded.  But what if we have emu + p-code + OCaml.pcd + new-lang.txt + demo-in.txt?  Each AI needs to figure this out and they get creative and try things that do not work or are very slow, like re-compiling, re-asembling each part every time for every test or demo.    So what I want is (a) a name for a tool that organizes/caches/vendors/verisions this in a repeatable/reproducible way, and (b) the tool (a CLI)'s arguments and config file schema to cover all the use-cases with some error checking, caching, etc. 

(a) naming. since this tool is only useful for cor24 emulator-related languages, it will be in the sw-embed org.  However, this tool is written in Rust and does not run on an emulated cor24 board.  So a language, say sw-cor24-basic or sw-cor24-ocaml follows a naming convention but sw-cor24-runner is misleading as it does not run on cor24 it runs things on cor24, so I need a different naming convenion.

(b) each higher level project needs to vendor its lower level dependencies somehow. This could be the config file passed to the runner.  The runner may need to cache certain versions since different dependent language runners may be tested against different versions of a dependency.  Both smalltalk and new language tuplet depend on p-code VM but different versions.  Note that the tool will be installed under ~/.local or similar and has its own subdir/cache. 

Help me describe a name and approach to delgate to a CLI AI Coding Agent to implement.

Core model
Think of each runnable demo/test as a scenario.

A scenario is not “run this file.” It is:

Build or fetch these pinned layers, place artifacts into emulator memory/UART/devices, then run with these limits and expected outputs.

Example stack:

cor24 emulator
  + monitor.bin
  + pcode_vm.bin
  + ocaml.pcd
  + new-lang.txt
  + demo-in.txt

its kind: assembler, binary, pcode, source, data

how it is produced

how it is loaded

whether it is cached

version/source identity

memory address or device channel

Config schema sketch
Use TOML first. It is readable, Rust-friendly, and easy for agents.

schema_version = 1

[project]
name = "sw-cor24-ocaml"
root = "."
default_scenario = "ocaml-newlang-demo"

[cache]
enabled = true
namespace = "sw-cor24-ocaml"
mode = "content-addressed"

[vendor]
lockfile = "cor24-launch.lock"
directory = ".cor24/vendor"

[tools.emulator]
kind = "host-binary"
path = "../sw-cor24-emu/target/release/cor24-emu"
version_command = ["../sw-cor24-emu/target/release/cor24-emu", "--version"]

[tools.assembler]
kind = "host-binary"
path = "../a24-sw/target/release/a24"
version_command = ["../a24-sw/target/release/a24", "--version"]

[tools.pcode_compiler]
kind = "host-binary"
path = "../pascal-sw/target/release/pascal-pcode"
version_command = ["../pascal-sw/target/release/pascal-pcode", "--version"]

Versioning and vendoring model
Each dependency should resolve to an immutable-ish artifact identity:

[dependencies.sw-cor24-pcode-vm]
source = "git"
repo = "https://github.com/softwarewrighter/sw-cor24-pcode-vm"
rev = "8f42abc"
artifact = "target/cor24/pcode-vm.bin"

[dependencies.sw-cor24-monitor]
source = "git"
repo = "https://github.com/softwarewrighter/sw-cor24-monitor"
tag = "v0.3.1"
artifact = "build/monitor.bin"
Generate lockfile:

[[locked]]
name = "sw-cor24-pcode-vm"
rev = "8f42abc..."
artifact_hash = "sha256:..."
cached_path = "~/.cache/sw-cor24-launch/artifacts/..."
Rules:

config declares intent

lockfile records exact resolved versions

cache stores built artifacts by hash

vendor directory stores source snapshots or checked-out dependencies

scenario run uses lockfile unless --update-lock is explicit

Cache key
Cache key should include:

tool path/version/hash
input file hashes
dependency artifact hashes
build args
target profile
load address if artifact is address-sensitive
schema version
For each layer:

layer_key = sha256(
  layer_config_normalized +
  input_hashes +
  tool_version +
  dependency_hashes
)
Error checking
The CLI should reject:

UART load larger than configured max_bytes

overlapping memory loads

missing tool paths

dirty/unlocked dependency versions unless allowed

source type loaded by impossible method

p-code app loaded without a VM layer

interpreter source missing when interpreter layer declares it required

cyclic layer dependencies

stale lockfile

binary artifact without known hash

scenario without termination condition

Useful diagnostics:

error: layer demo_input overlaps with ocaml_pcode
  demo_input: 0x00C000..0x00D2A0
  ocaml_pcode: 0x008000..0x00CFFF
suggestion: move demo_input to 0x00D000
